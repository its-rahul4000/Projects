Cybersecurity Log Intelligence System - Project Requirements

1. Secure Coding Requirements

* The project must strictly follow secure coding guidelines and industry best practices.
* The implementation shall include:

  * Input validation and sanitization.
  * Secure file upload validation.
  * Secure authentication and password hashing using modern algorithms (preferably Argon2id).
  * Parameterized database queries to prevent SQL injection.
  * Proper exception handling and secure logging.
  * Principle of least privilege for all users and components.
  * Dependency vulnerability scanning.
  * Secure secret and credential management.
  * Secure file handling and path validation.
  * Static code analysis using tools such as Bandit, Semgrep, or equivalent.
* The project shall use secure, well-maintained, and industry-standard libraries with no known critical vulnerabilities.
* The project should always use the latest stable version of Python and the latest secure versions of all dependent libraries.
* YAML configuration files should be used wherever appropriate for application configuration and rule management.

2. Project Architecture

* The system shall be scalable and designed for future expansion.
* The codebase shall be modular and flexible so that new features can be added with minimal changes.
* The project shall contain a single main.py entry point that automatically starts both the backend and frontend components.
* The repository shall include a properly maintained README.md that enables anyone to set up and run the project on their own system.
* The source code shall be well documented with meaningful comments to improve readability and maintainability.

* Administrator

5. IT Owner Registration and Authentication

* IT Owners shall register through the web dashboard.
* During registration, the IT Owner shall provide:

  * Desired User ID.
  * Email address.

* The system shall verify that the requested User ID is available.
* Upon successful registration, the system shall generate a unique random temporary password and send it to the registered email address.
* The temporary password shall be different for every registration.
* After first login, the IT Owner shall be required to change the temporary password to a new password of their choice.
* IT Owners shall be able to log out securely.
* User sessions shall automatically terminate after 15 minutes of inactivity.

6. Password Policy

* Both Administrator and IT Owner passwords shall have a minimum length of 20 characters.
* Passwords shall be securely hashed before storage.
* IT Owner passwords shall expire after 180 days.
* Upon expiration, users shall be required to change their passwords before continuing to use the system and change password notification will pop out.

7. Threat Detection Rules Management

The system shall support:

* Static Rules.
* Dynamic Rules with configurable threshold values.

Only the Administrator shall have permission to:

* Create rules.
* Update rules.
* Delete rules.
* Configure threshold values.
* Enable or disable rules.
* Define the default rule set.
* Apply updated rule configurations globally to all IT Owners.

Whenever the Administrator applies rule changes, those updates shall automatically become effective for all IT Owners.

IT Owners shall have **read-only access** to the list of threat detection rules so that they can view and understand which rules are currently active and applied by the Administrator.

IT Owners shall not be permitted to:

* Create rules.
* Modify rules.
* Delete rules.
* Configure threshold values.
* Enable or disable rules.
* Override Administrator-defined configurations.
* Select or deselect threat detection rules before analysis.

Every analysis performed by an IT Owner shall always use the latest Administrator-approved rule set.


8. Log Upload and Analysis

Both Administrators and IT Owners shall be able to:

* Upload supported log files.
* Execute automated threat analysis.
* View dashboards and visualizations.
* View detected threats.
* Generate PDF reports.

9. Append Analysis

The web dashboard shall include an "Append Analysis" feature.

When selected:

* The newly uploaded log file shall be merged with the existing analysis session.
* The system shall extend the existing analysis and reporting results.
* Email notifications shall include the updated analysis information.

When not selected:

* Uploading another log file shall start an entirely new analysis session.
* Previous analysis results shall not be combined with the new upload.

10. Report Generation

* Users shall be able to generate PDF reports after analysis.
* Reports shall be downloaded directly through the browser to the user's local Downloads folder.
* Whenever an Administrator or an IT Owner performs an analysis, the generated PDF report shall be emailed **only to the email address of the user who uploaded the log file**.
* If the uploader is an Administrator, the report shall be emailed to the Administrator's registered email address.
* If the uploader is an IT Owner, the report shall be emailed to that IT Owner's registered email address.
* The system shall not send duplicate report emails to other users unless such functionality is explicitly configured in the future.


11. Data Retention

* Analysis reports shall not be permanently stored in the system database.
* Only audit logs and essential operational records shall be retained.
* Temporary reports, uploaded log files, generated analysis artifacts, and temporary generated files shall be deleted after logout, session expiration, or completion of the configured cleanup process.
* Application itself-generated audit logs shall be retained for a maximum of 180 days and automatically deleted thereafter.

12. Security and Maintainability

* The project shall be designed to support future version upgrades.
* New functionality should be easily integrated without major architectural changes.
* Secure coding practices shall be followed throughout development.
* The application shall be resilient, maintainable, and suitable for enterprise-scale deployment.

13. Supported Log File Formats

The system shall support secure upload and analysis of multiple industry-standard log formats, including but not limited to:

* .log, .txt
* .syslog
* .cef
* .log


14. Audit Logging(Log of Cybersecurity Monitoring System)

The system shall maintain audit logs for security-sensitive operations, including but not limited to:

* Timestamp of required period
* User registration.
* User login and logout.
* Password changes.
* file name of log file uploaded
* Administrator rule modifications.
* Administrator user management actions.

Audit logs shall be retained for 180 days and automatically deleted after the retention period.

15. Temporary File Management

* Uploaded log files, generated analysis artifacts, and temporary PDF reports shall be treated as temporary data.
* Files shall only exist for the duration required to complete analysis or download.
* Temporary files shall be automatically removed upon user logout, session expiration, or completion of the configured cleanup process.
* The system shall avoid permanently storing uploaded logs or generated reports unless explicitly required for audit purposes.

16. Session Security

The application shall enforce secure session management by:

* Automatically terminating inactive sessions after 15 minutes.
* Invalidating all associated session tokens upon logout or timeout.
* Clearing any temporary analysis data associated with the expired session.
* Redirecting the user to the login page after automatic logout.

17. Database Security

The database shall follow secure development practices, including:

* Storage of passwords only as secure password hashes.
* Use of parameterized queries or ORM protections to prevent SQL injection.
* Enforcement of role-based access control for all database operations.
* Secure initialization of the default Administrator account during first-time setup.
* Protection against unauthorized direct database modifications.

18. Rule Application Policy

* The threat detection engine shall always execute using the currently active Administrator-approved rule set.
* IT Owners shall have read-only visibility of the configured threat detection rules and may review the list of rules applied by the Administrator.
* IT Owners shall have no ability to modify, customize, create, update, delete, enable, disable, select, or deselect threat detection rules.
* Any rule updates applied by the Administrator shall automatically become effective for all subsequent analyses performed by every IT Owner without requiring additional configuration.


19. Email Notification Policy

For every completed analysis initiated by either an Administrator or an IT Owner:

* The generated PDF report shall be emailed **only to the registered email address of the user who uploaded the log file**.
* If the analysis is initiated by the Administrator, the report shall be emailed only to the Administrator.
* If the analysis is initiated by an IT Owner, the report shall be emailed only to that IT Owner.
* When Append Analysis is used, the email shall reflect the combined analysis results and include the updated PDF report generated for the appended analysis.
* During IT Owner registration, the system shall generate a unique temporary password and send it only to the registering IT Owner's email address.


20. Maintainability and Versioning

* The project architecture shall support future enhancements through modular design and version-controlled components.
* Configuration values, security settings, and threat detection rules shall be externalized where appropriate (for example, using YAML configuration files) to minimize code changes during future updates.
* The system shall be designed so that new features, detection rules, dashboards, and integrations can be added with minimal impact on existing functionality.
